# องก์ที่ 1: The Hook

ลองจินตนาการถึงโค้ดส่วนเดียวที่ควบคุมทุกอย่างในแอปพลิเคชันของคุณ ไม่ว่าจะเป็นการยืนยันตัวตนผู้ใช้ การเชื่อมต่อฐานข้อมูล การแจ้งเตือนทางอีเมล และแม้กระทั่งตรรกะของ UI ในตอนแรกมันดูเหมือนจะสะดวกสบาย แต่ไม่นานมันก็จะกลายเป็นอสูรกายขนาดมหึมาที่ไม่สามารถดูแลรักษาได้ สิ่งนี้เรียกว่า "The God Object"

<Callout title="Socratic AI Prompt" type="info">
หากคลาสเดียวมีหน้าที่รับผิดชอบการทำงานหลักทั้งหมดในแอปพลิเคชัน จะเกิดอะไรขึ้นเมื่อคุณต้องการเปลี่ยนรูปแบบการส่งอีเมล? สิ่งนี้ส่งผลต่อโค้ดการเชื่อมต่อฐานข้อมูลที่อยู่ในคลาสเดียวกันอย่างไร?
</Callout>

# องก์ที่ 2: Mental Model

เพื่อให้เข้าใจถึงวิธีการทลาย God Object เราต้องนำเสนอหลักการ SOLID โดยเฉพาะอย่างยิ่ง Single Responsibility Principle (SRP) ให้คิดว่าแอปพลิเคชันของคุณเหมือนกับร้านอาหาร หากพ่อครัวต้องรับออเดอร์ เสิร์ฟอาหาร และจัดการเรื่องการชำระเงินด้วย ความวุ่นวายก็จะเกิดขึ้น ความรับผิดชอบจึงต้องถูกแบ่งออกไปยังบทบาทที่เชี่ยวชาญเฉพาะทางแทน

<Callout title="Socratic AI Prompt" type="info">
คุณจะปรับปรุงสถานการณ์ในร้านอาหารที่พ่อครัวทำทุกอย่างได้อย่างไร? คุณสามารถเปรียบเทียบระหว่างการแบ่งบทบาทในร้านอาหารกับการแบ่งความรับผิดชอบของโค้ดได้หรือไม่?
</Callout>

# องก์ที่ 3: The Rabbit Hole

ตอนนี้ลองดูส่วนของโค้ดที่ให้มาด้านล่างนี้ มันแสดงถึง God Object ในระบบอีคอมเมิร์ซสมมติ งานของคุณคือการระบุความรับผิดชอบที่หลากหลายของมัน และประยุกต์ใช้หลักการ SOLID เพื่อแยกย่อยมันออกมา

```python
class ECommerceSystem:
    def process_order(self, order):
        # process payment
        # update inventory
        # send confirmation email
        pass
```

<Callout title="Socratic AI Prompt" type="info">
ความรับผิดชอบที่แตกต่างกันซึ่งซ่อนอยู่ในเมธอด `process_order` มีอะไรบ้าง? การแยกสิ่งเหล่านี้ออกเป็นคลาสย่อยๆ จะช่วยปรับปรุงความสามารถในการทดสอบและความยืดหยุ่นต่อการเปลี่ยนแปลงของระบบได้อย่างไร?
</Callout>
