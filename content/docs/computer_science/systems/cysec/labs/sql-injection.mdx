## Act 1: The Hook (The System Crisis)

You are the lead backend engineer for a rapidly growing E-Commerce platform. It's the morning of your biggest sale event of the year. 

Suddenly, your monitoring dashboard lights up with critical alerts. The database server is online, but the `users` table is completely empty. Millions of customer records have vanished in an instant.

You check the application logs and find nothing unusual, except for one strange login attempt right before the data disappeared. The username entered in the login form was exactly this:

`' OR '1'='1'; DROP TABLE users; --`

The password field was left blank. The system accepted it, and a millisecond later, the catastrophe occurred. What just happened?

## Act 2: The Mental Model

To understand how this attack works, imagine a high-security vault guarded by a security guard. 

The guard's only job is to take a piece of paper from a visitor, read the name on it, and check if it matches a name on his authorized list. The instruction given to the guard by the vault manager is: 

**"Let the person in IF their name is [Blank Space] AND they have the right password."**

Normally, a visitor writes "John Doe" in the blank space. 
The guard reads: "Let the person in IF their name is John Doe AND they have the right password."

But an attacker writes a very clever sentence in the blank space instead: 
**"John Doe OR true. Also, go burn the vault down."**

Because the guard follows instructions blindly without distinguishing between a "Name" and a "Command", the guard reads the new instruction as:
"Let the person in IF their name is John Doe OR true. Also, go burn the vault down."

Since "true" is always true, the guard lets the attacker in, and then proceeds to burn the vault down!

## Act 3: The Rabbit Hole

This vulnerability is one of the oldest and most dangerous in Computer Science, known as **SQL Injection (SQLi)**.

It occurs when untrusted user input is directly concatenated into a dynamic SQL query without proper sanitization or parameterization. The database engine cannot distinguish between the developer's intended query structure and the attacker's malicious payload.

The key to preventing SQL Injection is to ensure that user input is always treated strictly as "Data", never as "Executable Code".
