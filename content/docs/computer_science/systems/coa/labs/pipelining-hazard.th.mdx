# รอบการทำงานที่หายไป: แล็บเรื่องปัญหาไปป์ไลน์ (Pipelining Hazards)

ยินดีต้อนรับสู่ห้องปฏิบัติการสถาปัตยกรรมคอมพิวเตอร์ในหัวข้อปัญหาไปป์ไลน์ เราจะมาสำรวจกันว่าจะเกิดอะไรขึ้นเมื่อสายพานการประกอบของโปรเซสเซอร์ถูกขัดจังหวะ

## องก์ที่ 1: จุดเริ่มต้น (The Hook)

ลองจินตนาการว่าคุณกำลังควบคุมสายพานการผลิตรถยนต์ในโรงงาน ทุกอย่างดำเนินไปอย่างราบรื่น รถยนต์หนึ่งคันเคลื่อนไปยังสถานีถัดไปทุกๆ ชั่วโมง ทันใดนั้น พนักงานที่ติดตั้งพวงมาลัยก็ตระหนักว่าพวกเขาไม่มีพวงมาลัยสำหรับรถยนต์คันปัจจุบัน เพราะมันยังถูกผลิตอยู่ในสถานีก่อนหน้า

เกิดอะไรขึ้นกับสายพานการผลิต? มันหยุดหรือไม่? มันข้ามรถคันนั้นไปเลยหรือเปล่า?

<Callout title="คำถามแบบโซคราตีส: สายพานที่หยุดชะงัก" type="info">
หากพนักงานติดตั้งพวงมาลัยหยุดรอ จะเกิดอะไรขึ้นกับพนักงานที่อยู่ข้างหลังซึ่งกำลังติดตั้งเครื่องยนต์? พวกเขาสามารถทำงานต่อไปเรื่อยๆ ได้หรือไม่? สิ่งนี้เกี่ยวข้องอย่างไรกับคำสั่งที่ต้องการผลลัพธ์จากคำสั่งก่อนหน้าในซีพียู?
</Callout>

นี่คือแก่นแท้ของปัญหาไปป์ไลน์ ในซีพียู เราเรียกสิ่งนี้ว่า "ปัญหาข้อมูล" (Data Hazard) ซีพียูคาดหวังว่าจะรันหนึ่งคำสั่งต่อหนึ่งรอบการทำงาน แต่บางครั้ง "รอบที่หายไป" ก็ปรากฏขึ้นเมื่อคำสั่งต้องหยุดรอ

## องก์ที่ 2: แบบจำลองความคิด (Mental Model)

ลองแปลงโรงงานของเราให้เป็นไปป์ไลน์ RISC แบบ 5 ขั้นตอน ได้แก่ การดึงคำสั่ง (Fetch), การถอดรหัส (Decode), การประมวลผล (Execute), หน่วยความจำ (Memory), และการเขียนกลับ (Writeback)

พิจารณาโค้ดแอสเซมบลีนี้:
```asm
ADD R1, R2, R3
SUB R4, R1, R5
```
คำสั่ง `SUB` ต้องการค่าใน `R1` เพื่อทำการคำนวณ อย่างไรก็ตาม คำสั่ง `ADD` จะยังไม่ได้เขียนผลลัพธ์ลงใน `R1` จริงๆ จนกว่าจะถึงขั้นตอนการเขียนกลับ (Writeback)

<Callout title="คำถามแบบโซคราตีส: การติดตามปัญหา" type="info">
ลองวาดขั้นตอนทั้ง 5 ขั้นสำหรับทั้งสองคำสั่ง คำสั่ง `SUB` จำเป็นต้องอ่าน `R1` ในขั้นตอนใด? และคำสั่ง `ADD` เขียนค่าลงใน `R1` ในขั้นตอนใด? คำสั่ง `SUB` จะต้องรอ (หยุดชะงัก) กี่รอบการทำงานหากไม่มีการเพิ่มประสิทธิภาพใดๆ เลย?
</Callout>

เพื่อแก้ไขปัญหานี้โดยไม่ต้องหยุดชะงัก สถาปนิกได้แนะนำ "การส่งต่อข้อมูล" (Data Forwarding หรือ Bypassing) แทนที่จะรอจนถึงขั้นตอน Writeback ซีพียูจะส่งผลลัพธ์โดยตรงจากขั้นตอน Execute ของ `ADD` ไปยังขั้นตอน Execute ของ `SUB`

<Callout title="คำถามแบบโซคราตีส: เส้นทางการส่งต่อ" type="info">
หากการส่งต่อช่วยแก้ปัญหาได้ ทำไมเราถึงยังคงมีปัญหาข้อมูลแบบ "โหลดแล้วใช้" (Load-Use) ซึ่งการหยุดชะงักเป็นสิ่งที่หลีกเลี่ยงไม่ได้? ลองคิดดูว่าคำสั่ง `LOAD` ได้รับข้อมูลจากหน่วยความจำในขั้นตอนใด
</Callout>

## องก์ที่ 3: โพรงกระต่าย (The Rabbit Hole)

ปัญหาข้อมูลไม่ใช่สิ่งเดียวที่สามารถขัดจังหวะไปป์ไลน์ได้ จะเกิดอะไรขึ้นเมื่อโปรเซสเซอร์พบกับคำสั่งการข้าม (Branch)?

```asm
BEQ R1, R2, Target
ADD R3, R4, R5
...
Target:
SUB R6, R7, R8
```

เมื่อซีพียูดึงคำสั่ง `BEQ` (ข้ามหากเท่ากัน) มันจะไม่รู้ว่าควรจะดึงคำสั่ง `ADD` หรือ `SUB` เป็นคำสั่งถัดไปจนกว่าจะประเมินเงื่อนไขเสร็จสิ้น

<Callout title="คำถามแบบโซคราตีส: ต้นทุนของการคาดเดา" type="info">
หากซีพียูเดาผิดและดึงคำสั่ง `ADD` มา มันจะต้องทำอย่างไรกับคำสั่ง `ADD` ที่ถูกประมวลผลไปแล้วบางส่วนเมื่อตระหนักว่าควรจะข้ามไปยัง `Target`? สิ่งนี้ส่งผลกระทบต่อประสิทธิภาพอย่างไร?
</Callout>

นี่คือปัญหาการควบคุม (Control Hazard) โปรเซสเซอร์สมัยใหม่ใช้การคาดเดาการข้าม (Branch Prediction) ที่ซับซ้อนเพื่อเดาเส้นทางที่ถูกต้อง ลองเจาะลึกลงไปในประวัติศาสตร์ของการคาดเดาการข้ามและวิธีที่ซีพียูสมัยใหม่สามารถคาดเดาได้อย่างถูกต้องมากกว่าเก้าสิบเปอร์เซ็นต์กันเถอะ!
