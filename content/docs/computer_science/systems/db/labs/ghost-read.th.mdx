# The Ghost Read

## องค์ที่ 1: จุดเริ่มต้น (The Hook)

ลองจินตนาการว่าคุณกำลังสร้างแอปพลิเคชันธนาคาร คุณต้องคำนวณยอดเงินรวมของทุกบัญชีสำหรับลูกค้าหนึ่งราย คุณเริ่มธุรกรรมและรันคำสั่งเพื่อรวมยอดเงิน ในขณะที่ธุรกรรมของคุณกำลังทำงาน มีอีกธุรกรรมหนึ่งเพิ่มบัญชีใหม่ให้กับลูกค้ารายเดียวกัน เมื่อคุณรันคำสั่งรวมยอดเงินอีกครั้งในธุรกรรมเดิม ยอดเงินรวมกลับเปลี่ยนไป คุณเพิ่งประสบกับ "Ghost Read" หรือ Phantom Read

<Callout title="คำถามโสกราตีส: ความผิดปกติ" type="info">
หากธุรกรรมควรจะถูกแยกออกจากกัน ทำไมคำสั่งที่สองจึงมองเห็นบัญชีใหม่? สมมติฐานใดเกี่ยวกับ "การแยก" (isolation) ที่ถูกละเมิดในที่นี้?
</Callout>

## องค์ที่ 2: แบบจำลองความคิด (Mental Model)

เพื่อทำความเข้าใจ Ghost Read เราต้องสำรวจระดับการแยกธุรกรรม (Transaction Isolation Levels) มาตรฐาน SQL กำหนดไว้สี่ระดับ: Read Uncommitted, Read Committed, Repeatable Read, และ Serializable

Phantom Read เกิดขึ้นเมื่อธุรกรรมรันคำสั่งที่คืนค่าชุดแถวที่ตรงตามเงื่อนไขการค้นหา และต่อมาพบว่าชุดแถวเหล่านั้นเปลี่ยนไปเมื่อรันคำสั่งซ้ำ เนื่องจากการทำงานของธุรกรรมอื่นที่เพิ่งเสร็จสมบูรณ์

<Callout title="คำถามโสกราตีส: Repeatable Read กับ Phantom Read" type="info">
ระดับการแยก "Repeatable Read" ป้องกันไม่ให้เกิด non-repeatable reads (ซึ่งข้อมูลของแถวเปลี่ยนไป) ทำไมมันจึงไม่จำเป็นต้องป้องกัน Phantom Reads เสมอไป? ลองคิดถึงความแตกต่างระหว่างการล็อกแถวที่มีอยู่กับการล็อกช่วงของเงื่อนไข
</Callout>

## องค์ที่ 3: โพรงกระต่าย (The Rabbit Hole)

หากเราต้องการหลีกเลี่ยง Phantom Reads อย่างสมบูรณ์ เราสามารถใช้ระดับการแยก "Serializable" ได้ อย่างไรก็ตาม สิ่งนี้มาพร้อมกับค่าใช้จ่ายด้านประสิทธิภาพที่สำคัญ

<Callout title="คำถามโสกราตีส: ราคาของความสมบูรณ์แบบ" type="info">
ฐานข้อมูลนำระดับการแยก Serializable ไปใช้งานจริงอย่างไร? หากทุกธุรกรรมทำงานราวกับว่ามันทำงานตามลำดับ จะเกิดอะไรขึ้นกับคำขอของผู้ใช้ที่เกิดขึ้นพร้อมกัน? มันคุ้มค่าเสมอไปหรือไม่ที่จะแลกประสิทธิภาพกับความสม่ำเสมอที่สมบูรณ์แบบ?
</Callout>
